## Architecture

### Provider owner and transport selection

Evolve the existing concrete Responses adapter behind `ResponsesClient`, rather than layering another provider client over `HTTPTransport`. Its shared responsibilities are dispatch preparation, provider policy, payload construction, error reduction, usage evidence, diagnostics, and HTTP compaction/model metadata. Add the SDK-managed socket as its generation resource. Keep the provider-neutral `Client.Generate` contract and the existing `ResponsesTransport` seam.

Select generation transport from an internal typed property of the registered provider variant. OpenAI, ChatGPT Codex, and the two public xAI variants select WebSockets. The Grok CLI proxy and generic Responses-compatible variants select HTTP/SSE. Capability overrides and model-name matching cannot enable WebSockets. No endpoint probe, transport setting, parallel send, or failure-based HTTP selection is needed. The selected variant's existing Responses policy governs both transports.

Use `responses.NewResponseService` with explicit base URL, Kent's HTTP client, selected-connection credentials and existing provider options, and SDK retries disabled. Do not construct a default SDK client that imports OpenAI environment credentials into Grok or another selected connection. HTTP compaction, including OpenAI V2's SSE operation, keeps its existing policy and payload path.

### Managed connection and ownership

One provider client owns at most one generation socket and one continuation checkpoint. `Connect` is lazy. Configure the approved message, queued-byte and queued-event limits through `ResponseConnectionOptions`. Use the SDK's ordinary default receiver without lanes or cross-Session multiplexing. Kent must not add a socket reader, receive queue, WebSocket codec, reconnect loop or duplicate response accumulator.

The existing runtime construction already creates distinct main and Reviewer clients. Their sockets follow their Engine's lifetime, including retirement by `server/sessionruntime/authority_idle.go`. Reuse each socket across completed Steps and human turns. Nano's existing per-invocation client belongs to that invocation and closes when it returns. Workflow and subagent Engines use the same provider construction and lifetime rules.

Expose resource cleanup through the standard optional `io.Closer` capability on the concrete resource-owning client and its existing wrappers, not a required method on every `llm.Client` implementation. Forward cleanup through `ResponsesClient`, the idle watchdog, and `observedModelClient`. Engine shutdown closes the currently owned main and Reviewer resources after interrupting active work. Existing connection replacement closes the displaced client, and Reviewer client replacement closes its displaced Reviewer resource. Nano closes its client on every return path. Aggregate cleanup failures with the operation error rather than swallowing them. No client registry, reference counting, global lock or new Runtime lifecycle is needed.

Keep socket and checkpoint mutation inside the provider owner. Its operation serialization protects that resource only. The SDK remains the sole socket reader. On generation cancellation, abort the specific socket used by that operation: SDK `Recv(ctx)` cancellation alone only stops waiting and does not stop provider generation. A scoped cancellation callback must be disarmed before successful return so the idle watchdog's later cleanup cannot abort a completed operation's reusable socket. SDK close/abort ends its reader and releases queued data. Stop, stalls, stream failures and Engine teardown must leave no usable checkpoint for an abandoned response.

### Sticky authentication and dispatch identity

Separate credential resolution from per-response dispatch projection in the existing dispatch preparation. Resolve credentials when opening the socket and retain the opening authentication mode/account with that socket. On an open socket, build current dispatch metadata using those opening facts without calling `ResolveDispatchAuth`. Reopen only for a later invocation/attempt after the socket is discarded, or when the existing connection owner replaces the entire selected Provider Connection. HTTP operations continue resolving authentication through their current path. No new auth cache, credential persistence or server-wide authentication policy is needed.

Use existing endpoint-specific options for handshake authentication, account, originator, user agent and Session routing. SDK `WithResponseInto` captures the handshake response, allowing the existing Codex turn-state observer and diagnostic header handling to work without wrapping the upgraded stream. Per-Step `x-codex-turn-metadata` already lives in `client_metadata` through `applyCodexClientMetadata`; send its current value on each create event. Do not mistake changing Step IDs or this metadata for a changed conversation prefix or a reason to reopen the socket. Model and generation controls belong to each create request.

### Shared prepared payload and event projection

Keep `RequestAsResponses`, the existing Responses payload builder, and `buildResponsesInput` authoritative. Input comes from provider-ready `ResponseItem.Raw`; selecting a suffix changes which complete items are transmitted, never their contents. Do not materialize a new historical representation or normalize already-sent items.

Bridge the builder's `ResponseNewParams` into the SDK's typed `ResponsesClientEventResponseCreateParam` using the SDK/Go JSON codecs, not a second field-by-field provider payload implementation. Apply the selected exact input slice and optional prior response ID to the create event. Carry provider extension fields, especially Codex `client_metadata`, through the existing policy hooks explicitly, since decoding into another generated parameter type must not lose extra fields. Leave `stream`, `background`, recovery options and lane routing unset.

Consume `ResponseConnection.Recv` until the response's terminal event rather than using `FinalResponse`, which would hide incremental callbacks. Adapt the SDK WebSocket event union to the existing SDK stream-event representation with typed JSON decoding for the common Responses event schema. Feed the existing `responseStreamAccumulator`, output parsers, stream activity callback and response/usage construction. Handle the typed nested WebSocket protocol-error event before this common stream projection. There must be one implementation of text, reasoning, tool-call accumulation and terminal response validation.

### Native output acceptance and persistence prerequisite

The earlier checkpoint proposal assumed parsed `OutputItems` already survived ordinary acceptance. They do not. `responseFromResponses` builds a simplified Assistant Message, `step_executor` commits that Message, and `chatStore.appendMessage` calls `ItemsFromMessages`. That reconstructs message/call IDs, Raw payloads and reasoning order differently from the received output. The existing reopen tests compare saved-request reconstruction across reload, not native provider output against the first subsequent request. They do not disprove this mismatch.

Extend the existing Message/MessageRecord model with an explicit native-provider-response body alternative. For newly accepted Responses output, that body owns the complete ordered native output items and the provider-format identity required to interpret them. Capture it from the terminal provider response, including opaque items, before the lossy Assistant projection. Its persisted payload must preserve the original item bytes through the JSON record codec, using an opaque byte-preserving field rather than decoding and re-encoding each item as a new JSON object.

For this native body, persist no parallel Content, ToolCalls or ReasoningItems representation of the same output. Derive those existing Message/UI/execution views through the existing output parser and response projection. Keep only local acceptance/presentation facts that cannot be derived from the native body, without copying the answer or tool arguments. Preserve the native source through phase handling, normalization, cloning, the existing assistant steering commit and Result Group persistence. Native context items must be committed even when they produce no visible assistant row. Existing accepted-call decisions still authorize tool execution; retaining a native call does not authorize a rejected call.

On live application and hydration, materialize the same native body before ordinary Message projections. `ItemsFromMessages` must project a native body to its existing parsed provider items in the original order with the original Raw bytes, rather than running the simplified-message reconstruction branch. The existing prepared-Raw passthrough then sends it unchanged. Message/item IDs, call_id, reasoning summaries/encrypted data, content blocks, opaque items and ordering must all survive acceptance and reload. UI/tool presentation is a derived view, not a competing provider-input source.

Existing generic Message records, including saved assistant Messages, keep their current reader and current prepared input. Human/local messages still need that body representation. New provider output uses the native body exclusively. This is the user-approved schema extension with no historical rewrite, migration scan, recovered/invented native IDs, new transcript event kind, or dual write. Reuse the existing Message event codec, coordinates, steering owner, and append/commit semantics. Complete this prerequisite and its real-Runtime boundary coverage before the main WebSocket integration.
